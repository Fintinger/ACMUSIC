# 屏蔽功能：前端 UX 设计建议

> 承接 `docs/API_BLACKLIST.md`（后端接口已就绪）。本文只谈产品与交互，不含实现代码。
> 2026-11-19

## 一、三条原则

1. **被动隐藏，主动标记。** 歌单、推荐、首页这类"喂给你的"场景，屏蔽内容直接不出现；搜索、歌手页这类"我自己找的"场景，保留但打标——否则用户会以为搜索坏了，也找不到解除入口。
2. **任何屏蔽都可撤销。** 至少两条路：操作后 5 秒内的 toast 撤销、管理页的解除按钮。
3. **两档强度分开。** 「屏蔽」是硬过滤（全局隐藏 + 播放跳过，账号级）；「不感兴趣」是软反馈（只影响推荐流）。不要合并成一个按钮，语义不同。

## 二、入口：在哪能屏蔽

按使用频率排优先级，不要一次铺满。

| 优先级 | 位置 | 具体落点 |
| --- | --- | --- |
| P0 | 迷你条「更多」 | `PlayerCore.vue` 的 `barRight` 末尾加 `⋯`，菜单：屏蔽这首歌 / 屏蔽这位歌手。展开播放大厅不放入口——那里是沉浸听歌，不该塞管理动作 |
| P0 | 歌曲行「更多」 | `TracksLayout.vue` 现有两个 hover 按钮收进 `⋯` 下拉（加入队列、加入歌单、屏蔽歌曲、屏蔽歌手） |
| P1 | 歌手页 | `ArtistDetail.vue` 的 `hero-actions`，关注按钮旁边加「屏蔽」 |
| P1 | 播放队列 | `PlayerCore.vue:281` 每项操作区，在「下一首播放 / 移除」之间 |
| P2 | 歌曲信息面板 | `SongInfoPanel.vue` 底部一行文字链「不喜欢这首歌？」 |
| P2 | 搜索结果 | 见第四节 |

为什么 P0 是播放器和行内：用户屏蔽的动机几乎都发生在"正在听"或"正在翻列表"的瞬间，跑到歌手页再屏蔽的路径太长。

**行内的坑**：`TracksLayout` 的 hover 操作区只有 24px 高，现在两个按钮刚好；直接加第三个会把时长列挤掉。必须收纳成 `⋯`，不要硬塞。

## 三、管理页：在哪查看

**建议独立路由 `/blacklist`，不要用弹窗。**

理由：名单可能几十上百条，弹窗高度撑不住；独立页可收藏、可从外部链接直达；与 `/daily`、`/annual` 同级，符合现有路由约定（`meta.level: 2`）。

入口两个：

1. **头像下拉菜单**（`App.vue`）：个人主页 / 主题颜色 / **音乐黑名单** / 更新日志 / 退出登录
2. **「我的」页**（`/me`）加一张入口卡片，和"创建歌单 / 收藏歌单"并列

页面结构：

```
音乐黑名单                                  [清空]
[ 歌曲 12 ] [ 歌手 3 ]
────────────────────────────────────────
🔍 在名单内搜索…
────────────────────────────────────────
封面  歌名            歌手        3 天前    [解除]
头像  歌手名          12 首歌     1 周前    [解除]
```

- 两个 tab：歌曲 / 歌手
- 数据链路：`/music/dislike/get` 拿 id 列表 → `/song/detail?ids=` 批量补歌曲信息；歌手没有批量接口，`/artist/detail?id=` 并发补，限 5 并发
- **必须带 `?t=Date.now()`**：`server.js:265` 有 2 分钟全局 GET 缓存，不带会看到旧名单
- 空态文案：「还没有屏蔽任何歌曲或歌手」，附一句「在播放器或歌曲列表里点 ⋯ 就能屏蔽」
- 底部说明：「屏蔽只作用于本账号，官方客户端同样生效」
- 「清空」走 `$confirmBox` 二次确认，文案写明条数

## 四、搜索里要不要展示已屏蔽的歌手

**要，而且必须展示。** 这是整套设计里最关键的一个决策。

三条理由：

1. 搜索是主动行为。隐藏结果会让用户判断成"搜不到"，而不是"我屏蔽过他"。
2. 只有展示，才有就地解除的路径。否则用户必须记得去管理页。
3. 用户经常只是想确认"我是不是屏蔽了他"。

具体表现：

- **歌曲结果**：灰显 + 行首「已屏蔽」角标 + 不可直接播放；点击时弹确认「这首歌已被屏蔽，是否解除并播放？」
- **歌手结果**：卡片半透明遮罩 + 「已屏蔽」标签，仍可点进歌手页
- **歌手详情页**：不 404、不拦截，顶部一条横幅：「你已屏蔽该歌手，其歌曲不会出现在推荐和列表中 [解除屏蔽]」
- **专辑 / 歌单结果**：不标记。屏蔽对象是歌和歌手，不是专辑，标了反而误导

实现上只需要给 `TracksLayout` 加一个 prop：

```js
blockedMode: 'hide' | 'mark'   // 默认 hide
```

- `hide`：歌单详情、专辑详情、每日推荐、首页（被动浏览）
- `mark`：搜索结果、歌词搜索（主动查找）

这是唯一需要给列表组件加"模式"的地方，其他页面不用感知屏蔽逻辑。

## 五、其他场景的处理

### 播放队列

- 屏蔽时把该歌从队列移除，提示「已从播放列表移除」；一次屏蔽歌手可能移除多首，提示带上数量
- **正在播的那首被屏蔽 → 立即切下一首**，不要停在上面
- 队列面板不渲染被屏蔽项（否则"下一首"还能点到）

### 每日推荐

屏蔽时顺带调 `/recommend/songs/dislike`（后端已有 module），让服务端补位。它的响应里带 `repushResource`，可以直接把那一行替换成补位歌曲——官方客户端就是这么做的，用户感知是"这一行换了一首"，而不是"少了一首"。

### 私人 FM / 心动模式

在取流层过滤：`utils/personalFm.js` 的 `collect()`、`utils/heartMode.js` 的 `fetchHeartBatch`。过滤后不足 3 首时，靠 `fetchFmBatch` 已有的补量循环自然拉下一批。

要防一个极端情况：屏蔽了大量歌手后推荐池被抽干，需要提示「推荐池里可播放的歌曲都已屏蔽」并给管理页入口，而不是一直转圈。

### 歌单详情

隐藏后总数对不上（显示 50 首、只列出 47 首），列表顶部加一行：「已屏蔽 3 首 · 查看」。

**管理模式必须不过滤**：`ListDetail.vue:67` 的插槽用 `index` 做上移/下移（`moveTrack(index, -1)` 直接操作 `songs` 数组），过滤后 index 错位会删错歌。进管理模式时先临时展示全部（灰显但可操作）。

### 未登录

屏蔽功能整体禁用，点击提示「登录后才能使用」。**不要做本地黑名单兜底**——两套数据源会让"我屏蔽了怎么换台设备又出现了"变成 bug 报告。

### 撤销

屏蔽成功后 5 秒 toast：「已屏蔽《XXX》 [撤销]」，点撤销直接调 delete 并恢复列表项。这是防误触最有效的一招，比二次确认的体验好——二次确认拦的是"手滑"，toast 撤销救的是"决策失误"。

## 六、文案与图标

- 统一用「屏蔽」，不用「拉黑」。网易云语境里"拉黑"指拉黑用户（社交），混用会误导。
- 确认弹窗必须写清影响范围：
  - 歌曲：「将从所有列表隐藏，播放时自动跳过。可在「音乐黑名单」中恢复。」
  - 歌手：「该歌手的所有歌曲（含合唱）都将隐藏。可在「音乐黑名单」中恢复。」
- 新增图标（`src/config/icon.js`，24×24、1.8px 描边）：`block`（禁止符号）、`more`（三点）、`blockArtist`（人像 + 禁止）

| 推荐过滤 | `utils/personalFm.js` 的 `collect`、`utils/heartMode.js` 的 `fetchHeartBatch` |

两处与设计不同：

1. **队列不物理移除**。设计里写"屏蔽时把歌从队列移除"，实现改成"跳过 + 队列里灰显划掉"。原因是物理移除必须同步修正 `curIndex`，而这个索引被 77 处代码依赖，`REPLACE_PLAYLIST` 与 `curIndex` watcher 之间很容易错位删错歌。用户感知一致：不会播到它，队列里能看到它被划掉。
2. **「我的」页入口未做**。目前只有头像菜单一个入口。`UserDetailLayout.vue` 有 80KB，结构复杂，为一张卡片动它的风险大于收益，等重做那块时再补。

另外两处小调整：

- `blockArtist` 图标没做（`block` 一个就够用）；`more` 图标项目里本来就有，没重复添加。
- 歌手详情页的"已屏蔽"横幅没做，改为 hero 区按钮本身的反色状态（「已屏蔽」红字）表达同一件事。
